# Representing the Shared Artifact Contract in n8n vs. CrewAI

The three schemas (`research_evidence.schema.json`, `analyst_artifact.schema.json`, `strategy_artifact.schema.json`) define one logical contract. Both implementations must produce data that satisfies the same shapes -- but the two platforms have fundamentally different native data models, and that difference is where behavior can silently diverge if you don't design for it deliberately. This is a walkthrough, not implementation code.

## The core difference in one sentence

**n8n moves a *list of items* between nodes, with no enforced typing unless you add it.** **CrewAI moves *typed Python objects* (Pydantic models) between tasks, with validation enforced by the framework by default.** Almost every divergence below is a consequence of that one difference.

## Concept-by-concept comparison

| Concept | n8n representation | CrewAI representation | Divergence risk |
|---|---|---|---|
| Basic data unit | A list of "items," each `{ json: {...}, binary?: {...} }`. Every node input/output is this list, even for a single object. | A plain Python object -- typically a `pydantic.BaseModel` instance, or a `list[BaseModel]`. No forced wrapper. | Low, as long as you consistently choose "one EvidenceRecord = one n8n item" or "one array field on one item" and document which -- see deep dive below. |
| Schema enforcement point | Not enforced by the platform itself. Closest equivalents: (a) a **Structured Output Parser** node attached to an AI Agent node, which can be given a JSON schema and will coerce/retry the LLM's output against it; (b) a manual **Code** node running your own validation (e.g. hand-rolled checks, or a bundled Ajv-style validator); (c) an **IF**/**Switch** node checking required keys exist before continuing. | Enforced by default: a `Task`'s `output_pydantic` (or `output_json`) makes the framework parse and validate the LLM's response against that model *before* the task is considered complete; a validation failure can trigger an automatic retry. | High if unaddressed. Without wiring a Structured Output Parser (or equivalent Code-node validation) into every agent step, n8n will happily pass a malformed EvidenceRecord downstream, while the CrewAI run would reject/retry the same malformed output. Equivalent reliability requires deliberately adding validation in n8n; it isn't free the way it is in CrewAI. |
| Enums (`CompetitorName`, `source_type`, `basis`, etc.) | No native enum type for LLM-generated JSON. A human-configured node (e.g. a dropdown in a Set node) can offer fixed choices, but *agent output* is only as enum-constrained as the JSON schema you hand to the Structured Output Parser, or a Code-node check you write yourself. | Maps directly to a Python `Enum` / `Literal[...]` type on a Pydantic field. Validated automatically -- an out-of-enum value is a validation error, not a silent pass-through. | Medium. If the n8n Structured Output Parser's schema omits the `enum` constraint (or a hand-written Code node forgets to check it), an LLM could emit `"AT&T Fiber"` instead of `"AT&T"` and it would flow through undetected, silently breaking joins on `competitor_name` in later tables. |
| Cross-step referencing | Expression syntax, e.g. `{{$json.evidence_id}}` or `{{$('Research Agent').item.json.claim}}`, scoped by node name and evaluated at run time. No compile-time check that the referenced field exists. | A real typed object: `analyst_output.competitor_comparison_table[0].competitor_name`. A missing/renamed field is caught by the type checker (if used) or raises immediately at run time, not silently returning `undefined`/empty string. | Medium-high. A typo'd n8n expression (`$json.evidenceId` vs `evidence_id`) resolves to an empty string rather than an error -- it can pass through several nodes before anyone notices a field is empty everywhere. |
| Evidence *array* (many `EvidenceRecord`s) | Two viable shapes, and they behave differently: **(a)** one n8n item per evidence record (natural if research sub-queries run as separate branches/parallel calls) -- then a later node must explicitly **Merge**/**Aggregate** those N items back into a single array before the Analyst step can consume "the evidence set" as one object; **(b)** the whole array kept as one field inside a single item (`{ evidence: [...] }`) from the start -- no merge step needed, but then per-record parallel processing (e.g. validating each link) needs an explicit "Split Out" step to fan back out. | Just a `list[EvidenceRecord]` (or `EvidenceSet` model wrapping one). Parallel fetches (if done via `asyncio.gather` or `crew.kickoff_for_each`) still resolve back into one ordinary Python list -- no split/merge ceremony at the data-model level. | High if the two shapes get mixed inconsistently within the same n8n workflow (e.g. some nodes assume "one item per record," others assume "one item holding the array") -- this is the single most common source of an n8n workflow silently processing only the first record, or crashing on `.length` of an object. Pick one shape for the whole evidence-array lifecycle and document the switch points explicitly. |
| Role/agent representation | Each of the four roles is typically a node (or sub-workflow invoked via **Execute Workflow**) chained by explicit connections; the "hand-off" is just that node's JSON output becoming the next node's input. | Each role is an `Agent` + one or more `Task`s, orchestrated by a `Crew` (sequential/hierarchical process) or a `Flow` with `@start`/`@listen`/`@router` steps and an explicit shared `state` object (often itself a Pydantic model) that can hold `brief`, `evidence`, `analyst_artifact`, `strategy_artifact` as it progresses. | Low for correctness, but structurally different enough that "compare the two workflows" (Step 11) needs to map "node" concepts to "Agent/Task" concepts rather than expecting a 1:1 file diff. A CrewAI **Flow**'s `state` object is the closer conceptual match to "the shared artifact contract" than a bare sequential Crew's task-to-task context passing. |
| Retry / error handling | Per-node "retry on fail" setting, with failures visible in the execution log; a failed node can be configured to continue-on-error or halt the workflow. | Task-level `max_retries` / tool-level retry logic in your own code, or a validation function on `output_pydantic` that triggers a re-prompt on failure. More manual/code-driven unless you lean on CrewAI's built-in guardrail-retry behavior. | Low-medium. Both are capable of equivalent behavior, but n8n's retry is closer to "free" (a checkbox), while CrewAI's is something you write -- easy to under-implement on the CrewAI side and end up with worse failure visibility than the n8n version, inverting the reliability comparison Step 11 asks you to make honestly. |
| Where the JSON Schema files actually get *used* | Not as a type system. Either pasted into a Structured Output Parser node's schema field (constrains one LLM call), or used purely as human documentation that you manually translate into Set-node field mappings and Code-node checks. | Nearly 1:1: each schema's `$defs` becomes an actual Pydantic `BaseModel` class (`EvidenceRecord`, `CitedField`, `AnalystArtifact`, ...) that you import and pass around -- the schema **is** close to the type system, not just documentation next to it. | Conceptual, not a bug risk, but worth naming: in n8n the schema's authority is "whatever you wired the Structured Output Parser and Code-node checks to enforce"; in CrewAI its authority is "the actual runtime type." If the two implementations' hand-translations of the same schema drift even slightly (e.g. n8n's parser schema omits the `pattern` regex on `evidence_id`), they're no longer really enforcing the same contract even though both point at the same `.schema.json` file. |

## Deep dive: the item-list vs. object-list difference, concretely

Say the Research Agent fans out three parallel calls (pricing, footprint, reviews) per competitor.

- **n8n:** each parallel branch naturally produces its own item(s). Before the Analyst node can build the competitor comparison table (which needs *all* competitors' data at once), you need an explicit **Merge** node (or **Aggregate**) to combine branches back into one list, and possibly a **Code** node to reshape that combined list into the `{ brief_id, evidence: [...] }` object shape `analyst_artifact.schema.json` expects as input. Skipping this step is the classic n8n bug: the Analyst node silently only sees whichever branch happened to arrive last.
- **CrewAI:** the three calls (however you parallelize them) each return a `list[EvidenceRecord]`; you concatenate them in ordinary code (`all_evidence = pricing + footprint + reviews`) before constructing the `EvidenceSet` passed into the Analyst task. There's no framework-level "did I remember to merge" trap -- but you can still introduce the same bug yourself if you forget to await/gather all three before concatenating (an `asyncio` bug now, not an n8n-wiring bug -- same failure mode, different cause).

Practical implication: whichever platform you're building, treat "assemble the complete evidence array before handing it to the Analyst step" as an explicit, testable checkpoint (this is exactly Step 4's "test the tools individually" and Step 5/6's "preserve the research evidence as a structured intermediate result" instructions) -- don't assume it falls out for free in either implementation.

## Deep dive: schema enforcement as config vs. as code

`analyst_artifact.schema.json`'s `CitedField.allOf` rule ("`evidence_ids` must be non-empty when `basis == 'evidence'`") is a real constraint we want enforced, not just documented.

- **CrewAI:** this becomes a Pydantic `model_validator` on the `CitedField` class -- a couple of lines of Python, checked automatically every time an instance is constructed, whether by your code or by parsing an LLM's tool-call output via `output_pydantic`.
- **n8n:** there is no native place this rule "lives." Your options are: give the Structured Output Parser node a JSON Schema that includes the same `if/then` conditional (many n8n LangChain-integration parser nodes accept standard JSON Schema, so this is often literally the same file); or add an explicit Code-node check after the AI Agent node runs, before letting the item continue downstream; or accept the gap and rely on the AI Agent's prompt instructions alone (weakest option -- prompt compliance isn't validation).

Practical implication: when you get to Step 4/5 (build/test the MCP layer and the n8n workflow), decide explicitly which of those three n8n options you're using for schema enforcement, and say so in the README (the guide asks for "logging, retry, budget, and caching decisions" documentation -- this belongs there too, since it's the same category of "decision that affects reliability and isn't visible from the workflow diagram alone").

## Summary checklist before building either implementation

- [ ] Decide once, in writing, whether the evidence array is "many items" or "one item with an array field" in n8n, and keep it consistent across every node that touches it.
- [ ] Confirm which n8n mechanism (Structured Output Parser schema, Code-node validation, or both) is enforcing each schema's `enum` and `allOf`/conditional rules -- don't rely on prompt instructions alone.
- [ ] In CrewAI, mirror every `$defs` type in the three schemas as an actual Pydantic model, including the `basis`-conditional validators, not just the top-level shape -- the conditional rules are exactly the parts easiest to drop when hand-translating JSON Schema into Python classes.
- [ ] Pick where the "shared state" lives structurally in each implementation (n8n: which node's output is the canonical `AnalystArtifact` snapshot; CrewAI: the `Flow` state object or the last task's `output_pydantic`) so Step 11's comparison table has a real like-for-like thing to point at in both.
